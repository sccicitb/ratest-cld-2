# Pillar 1 — Vision (READY TO BUILD)

## Requirements (decided)
- **Inline chat only.** Images attached in the composer are sent to the
  vision model (Qwen3-VL) as image content blocks. **KB stays text-only** —
  standalone images are NOT accepted into the knowledge base (backend
  `SUPPORTED_KB_TYPES` unchanged; KB upload keeps rejecting images).
- **Multiple images per message.**
- **Persist across turns:** images are stored and re-fed to the model on
  follow-up turns (so "look again at the top-left of that chart" works later).
  Reloading the chat must still show the images.
- **No downscaling; enforce a max image size** instead (reject oversized).
- Supported image types: `.png`, `.jpg`, `.jpeg` (already in the frontend
  picker allow-list; today they fail server-side — this pillar fixes that).

## Key design notes
- Today inline attachments go through `extract_text()`, which raises on images.
  The vision path must **bypass extraction**: an image attachment is stored as a
  blob, marked as an image, and never sent to `extract_text` / the KB.
- The chat model call must support **content arrays** (OpenAI vision shape):
  `content: [{type:"text",text}, {type:"image_url", image_url:{url:"data:image/png;base64,…"}}]`.
  Today `ModelClient.stream` + history use plain string `content`; this pillar
  extends that to allow the array form for messages that carry images.
- **Persistence + re-feed:** image attachments are linked to the user `Message`
  (the attachment-linking from Stage 6 already does this). When building model
  history, for each past user message that has image attachments, rebuild its
  image blocks. **Cap the number of re-fed images** (config, e.g. last N) to
  bound token cost/latency.
- **Serving images to the browser:** the frontend needs a real URL to render a
  thumbnail. Today an attachment's `url` is the opaque `storage_key`. Add an
  auth'd endpoint that streams an attachment's bytes so the bubble can show it.

## New/changed config
- `max_image_bytes` (e.g. 10 MB) — reject larger image attachments.
- `max_vision_images_per_turn` re-fed from history (e.g. 6) — token guard.
- (image extensions handled in the attachment path, not in `SUPPORTED_KB_TYPES`).

## Staged implementation plan (weights: 1pt ≈ half-day)

### Stage V1 — Image attachment intake + blob serving (weight 3, M)
Branch `v1.1-vision-intake`.
- [ ] Extend the chat attachment upload (`app/sessions/attachments.py`) to detect
      image types and route them down an **image path** that skips
      `extract_text`/ingest: store the blob, create an `Attachment` with an
      `is_image`/type marker and `ingested=False`, emit `attachment_resolved`.
      Enforce `max_image_bytes` → `error` event if exceeded.
- [ ] Add an auth'd, ownership-checked endpoint to stream an attachment's bytes
      (e.g. `GET /api/sessions/{sid}/attachments/{aid}/raw`) with the right
      content-type, so the SPA can render the image. (KB upload path untouched —
      still rejects images.)
- [ ] Tests: image upload → `attachment_resolved` (not ingested, no Qdrant);
      oversized → error; the raw endpoint returns the bytes for the owner and
      404s for another user; a non-image still extracts as today.

### Stage V2 — Vision in the chat loop (weight 3, M)
Branch `v1.1-vision-loop`. BASE: V1.
- [ ] Extend the chat path so a turn with image attachments builds an OpenAI
      **content-array** user message (text + `image_url` base64 blocks) instead of
      plain text. `ModelClient`/`run_turn` accept array content.
- [ ] **Re-feed across turns:** when building history, for past user messages
      with image attachments, rebuild their image blocks (capped at
      `max_vision_images_per_turn`, most-recent-first).
- [ ] Tests with a fake model client: assert the model receives image blocks for
      the current turn AND for a prior turn's image (persistence); cap respected;
      a text-only turn is unchanged (still a plain string, no regression).
- [ ] **Real smoke** against Qwen3-VL on llama-server: send an actual image,
      confirm the model describes it; ask a follow-up that needs the image again
      and confirm it still "sees" it. (Controller-run, like prior smokes.)

### Stage V3 — Frontend: multi-image compose + thumbnails (weight 2, M)
Branch `v1.1-vision-fe`. BASE: V2.
- [ ] Composer: accept multiple images, show pending thumbnails, send via the
      existing upload→chat flow (images resolve as image attachments).
- [ ] `MessageBubble`: render image attachments as **thumbnails** (from the raw
      endpoint), click-to-enlarge; keep the file-chip for non-images.
- [ ] On chat reload, persisted image attachments render from history.
- [ ] Typecheck + build; verify end-to-end in the browser with the real backend.

# Pillar 2 — Accounts + per-account MCP (REQUIREMENTS + OPEN)

## Decided
- **Real multi-user accounts.** Per-user data isolation already exists (sessions,
  KB, retrieval scoped by `user_id`).
- **Admin-provisioned users — no public signup.** An admin creates accounts.
- **Admin-assigned, per-account MCP:** admin curates a catalog of MCP servers and
  assigns which servers each account gets. **No user-supplied URLs/tokens.**
- **Lazy tool loading = account-enabled only:** the model is offered exactly the
  tools assigned to that account (no discovery meta-tool).
- **Shared org KB** (eventually): the `kb` scope becomes org-wide rather than
  per-user; **tags** do double duty — topical metadata filter (accounting,
  production…) AND org/access scoping. Session scope stays per-user/session.

## ⚠️ Locked-spec impact (needs sign-off)
Shared KB changes the **§8 scope filter** in the LOCKED `BACKEND_SPEC.md`
(today `user_id == caller AND …`). Before implementing, we agree the exact new
filter (e.g. `(scope==kb AND <org/tag access>) OR (scope==session AND
session_id==current AND user_id==caller)`) and I bring you the precise spec edit
to approve.

## OPEN — to resolve before staging (needs more talk)
1. **Admin bootstrap:** how is the first admin created (seed/env)? Is "admin" a
   role flag on a user, or a separate concept?
2. **User provisioning UX:** admin creates user with email + temp password? Password
   reset/change flow? Any per-user metadata (department/group)?
3. **MCP catalog + assignment model:** where stored (DB tables), and is assignment
   per-user, or per-group/role (e.g. "accounting" group gets the accounting MCP)?
4. **Secret storage:** admin-entered MCP bearer tokens — encrypted at rest? key mgmt?
5. **Connection lifecycle:** today MCP connects once at startup (global). Per-account
   means connect-per-session / on-demand, with caching + failure isolation. Pooling?
6. **Shared-KB access via tags:** the core design — do accounts carry granted tags
   (or groups)? Does upload set a doc's org/access tags? How does an admin manage
   "who can see what"? (Your stated need — let's design this together.)
7. **Your additional needs** for accounts/MCP (you mentioned you have some).

# Pillar 3 — Artifacts / canvas (DECIDED — ready to stage)

## The use case
User asks → the model loops (get big data via MCP/`download_url` → `execute_code`
analysis → summaries) → **the model writes an interactive HTML report** (sentiment/
data analysis) → shown live in a canvas panel → exportable to PDF. The HTML report
IS the artifact.

## Decided
- **Type: model-authored HTML reports only** (HTML/CSS/JS). `execute_code` stays
  analysis-only — it returns summaries the model embeds (Chart.js/Plotly/tables) in
  the report. No sandbox file-capture / no chart-PNG artifacts this pillar.
- **Generation: a native `create_artifact` tool.** The model calls it with
  `{artifact_id?, title, html}`. No `artifact_id` → new artifact; matching
  `artifact_id` (from a prior tool result, same session) → a **new version** of that
  artifact. (Adding a tool changes the registry, not the loop — §12.2.) `session_id`
  comes from `ctx`, never model args.
- **Versioned:** follow-ups ("add a pie chart") revise the same artifact → v1, v2…
- **Canvas shows the LATEST artifact** (its latest version). Older artifacts remain
  reachable via inline cards in their messages. (No multi-artifact switcher in the
  canvas for v1.1.)
- **Render: a sandboxed `<iframe>`** — `sandbox="allow-scripts allow-modals"` (NO
  `allow-same-origin`), so the report's JS runs in an **opaque origin**, walled from
  the app (no access to the auth token/cookies). A CSP limits egress.
- **Persisted:** each version's HTML stored as a blob + an artifact/version record
  linked to the session + the producing assistant message → survives reload.
- **PDF: client-side print** (`iframe.contentWindow.print()` → "Save as PDF").
  Accepted caveat: heavily-interactive JS charts may print imperfectly. No headless
  browser, no new infra.
- **`artifact` SSE event** (the rich-output extension the locked spec anticipated):
  carries metadata `{type:"artifact", artifactId, version, title}`; the HTML is
  fetched separately via an authed endpoint (HTML can be large — keep it out of the
  event stream).

## Staged plan (weights: 1pt ≈ half-day)

### Stage A1 — Artifact backend: model + tool + storage + SSE (weight 5, L)
Branch `v1.1-artifacts-backend`.
- [ ] Data model + Alembic migration: `Artifact(id, session_id, title, latest_version,
      created_at, updated_at)` + `ArtifactVersion(artifact_id, version, storage_key,
      message_id, created_at)`. (Or an equivalent single-table-with-versions design.)
- [ ] `create_artifact` native tool (`app/tools/builtin/`): args `{artifact_id?: str,
      title: str, html: str}`; `session_id` from `ctx`. New artifact (v1) or new
      version of an existing one (owned by this session). Store the HTML blob; return
      `{artifact_id, version}` text to the model so it can update later. Register it.
- [ ] Link a turn's created/updated artifacts to the assistant `Message` once it's
      persisted (mirror the attachment-linking pattern in `run_turn`).
- [ ] `artifact` SSE event in `app/chat/events.py`, emitted when the tool runs.
- [ ] Authed serve endpoint `GET /api/sessions/{sid}/artifacts/{aid}/raw[?version=N]`
      (default latest) → `text/html`; ownership via session. List/link artifacts so a
      reloaded chat can rebuild inline cards + the latest-canvas (e.g. include artifact
      refs in `GET /messages`, or a `GET /sessions/{sid}/artifacts`).
- [ ] Tests: tool creates v1; same `artifact_id` → v2; `session_id` from ctx not args;
      `artifact` event streamed; raw endpoint serves the HTML for the owner, 404 cross-user;
      reload listing works.

### Stage A2 — Frontend: canvas + inline card + render + PDF (weight 5, M-L)
Branch `v1.1-artifacts-fe`. BASE: A1.
- [ ] `chat.ts`: add `ArtifactEvent` to the `StreamEvent` union; `useStreamChat` tracks
      the current artifact (id, version, title).
- [ ] Canvas panel (Sheet/side-panel, like `SourcesDrawer`): renders the latest
      artifact's HTML in a **sandboxed iframe** (`srcdoc`, `sandbox="allow-scripts
      allow-modals"`), fetched via an authed call (like `AuthedImage`); version badge.
- [ ] Inline **artifact card** in the assistant bubble (title + version + "Open" →
      canvas). Auto-open the canvas on a fresh `artifact` event (configurable).
- [ ] **Export PDF** button → `iframe.contentWindow.print()`.
- [ ] Reload: load the session's artifacts; canvas shows the latest; inline cards
      render from message linkage. Typecheck + build; controller verifies end-to-end.
