# Pillar 1 — Vision (READY TO BUILD)

## Requirements (decided)
- **Inline chat only.** Images attached in the composer are sent to the
  vision model (Qwen3-VL) as image content blocks. **KB stays text-only** —
  standalone images are NOT accepted into the knowledge base (backend
  `SUPPORTED_KB_TYPES` unchanged; KB upload keeps rejecting images).
- **Multiple images per message.**
- **Persist across turns:** images are stored and re-fed to the model on
  follow-up turns (so "look again at the top-left of that chart" works later).
  Reloading the chat must still show the images.
- **No downscaling; enforce a max image size** instead (reject oversized).
- Supported image types: `.png`, `.jpg`, `.jpeg` (already in the frontend
  picker allow-list; today they fail server-side — this pillar fixes that).

## Key design notes
- Today inline attachments go through `extract_text()`, which raises on images.
  The vision path must **bypass extraction**: an image attachment is stored as a
  blob, marked as an image, and never sent to `extract_text` / the KB.
- The chat model call must support **content arrays** (OpenAI vision shape):
  `content: [{type:"text",text}, {type:"image_url", image_url:{url:"data:image/png;base64,…"}}]`.
  Today `ModelClient.stream` + history use plain string `content`; this pillar
  extends that to allow the array form for messages that carry images.
- **Persistence + re-feed:** image attachments are linked to the user `Message`
  (the attachment-linking from Stage 6 already does this). When building model
  history, for each past user message that has image attachments, rebuild its
  image blocks. **Cap the number of re-fed images** (config, e.g. last N) to
  bound token cost/latency.
- **Serving images to the browser:** the frontend needs a real URL to render a
  thumbnail. Today an attachment's `url` is the opaque `storage_key`. Add an
  auth'd endpoint that streams an attachment's bytes so the bubble can show it.

## New/changed config
- `max_image_bytes` (e.g. 10 MB) — reject larger image attachments.
- `max_vision_images_per_turn` re-fed from history (e.g. 6) — token guard.
- (image extensions handled in the attachment path, not in `SUPPORTED_KB_TYPES`).

## Staged implementation plan (weights: 1pt ≈ half-day)

Branch `v1.1-vision-intake`.
- [ ] Extend the chat attachment upload (`app/sessions/attachments.py`) to detect

# Pillar 2 — Accounts + per-account MCP (DECIDED — ready to stage)

## The core model: Group is the single access currency

**A `Group` is an atomic access unit** (a named bucket — e.g. "Accounting Store A").
It is NOT decomposed into tags. One `Group` entity gates BOTH KB access and MCP
access. **Tags stay exactly as in v1.0** — topical search filters, with **no
access role** (this is the key simplification: access and topics are separate
concerns).

```
User ──< member of >── Group ──< grants >── MCP servers
                          │
                  KBdoc belongs to EXACTLY ONE Group   (+ a public flag)
```

- **Accounts:** real multi-user, **admin-provisioned** (no public signup).
  `is_admin` boolean on the user; first admin bootstrapped via env/seed.
- **Groups:** users are members of one or more groups (many-to-many). A group is
  just a name + its grants. Admin creates groups and assigns membership.
- **KB access (the rule):**
  ```
  visible(kb_doc) =  kb_doc.is_public  OR  kb_doc.group_id ∈ caller's group_ids
  ```
  Atomic groups → no AND/OR tag math, no cross-store leak. "Store A Ops" and
  "Store B Ops" are simply two different groups.
- **KB uploads:** users keep uploading. A regular user's upload is **auto-filed to
  their group** (multi-group user picks WHICH of their groups from a dropdown — no
  free tagging). Admins upload + choose any group, toggle `public`, and set
  free topical tags. `uploaded_by` recorded; users manage (delete/reindex) only
  their own uploads, admins manage all.
- **Per-account MCP:** an admin-curated **catalog** of MCP servers (in the DB);
  each **group grants** a set of servers. A user is offered exactly the union of
  their groups' servers (account-enabled loading, no discovery meta-tool).
  Bearer tokens **encrypted at rest** (app key from env, e.g. Fernet).
- **Connection lifecycle:** the global startup MCP pool is replaced by **per-request
  resolution** from the caller's groups, with caching + failure isolation.
- **Admin UI:** a full `/admin` page — manage users, groups + membership, the MCP
  catalog, and group→server assignment.

## ⚠️ Locked-spec impact (needs sign-off before M3)
Shared KB changes the **§8 scope filter** in the LOCKED `BACKEND_SPEC.md`. Today:
`user_id == caller AND status == ready AND (kb OR session)`. New:
```
status == "ready" AND (
   (scope == "kb"      AND (is_public OR group_id ∈ caller_group_ids))   ← org-shared, group-gated
   OR
   (scope == "session" AND session_id == current AND user_id == caller)  ← still private
)
```
KB drops the `user_id == caller` gate (becomes org-shared by group); session files
stay private. **I bring the exact `BACKEND_SPEC.md §8` edit for explicit approval
at the start of Stage M3 — no spec change without sign-off.**

# Pillar 3 — Artifacts / canvas (DECIDED — ready to stage)

## The use case
User asks → the model loops (get big data via MCP/`download_url` → `execute_code`
analysis → summaries) → **the model writes an interactive HTML report** (sentiment/
data analysis) → shown live in a canvas panel → exportable to PDF. The HTML report
IS the artifact.

## Decided
- **Type: model-authored HTML reports only** (HTML/CSS/JS). `execute_code` stays
  analysis-only — it returns summaries the model embeds (Chart.js/Plotly/tables) in
  the report. No sandbox file-capture / no chart-PNG artifacts this pillar.
- **Generation: a native `create_artifact` tool.** The model calls it with
  `{artifact_id?, title, html}`. No `artifact_id` → new artifact; matching
  `artifact_id` (from a prior tool result, same session) → a **new version** of that
  artifact. (Adding a tool changes the registry, not the loop — §12.2.) `session_id`
  comes from `ctx`, never model args.
- **Versioned:** follow-ups ("add a pie chart") revise the same artifact → v1, v2…
- **Canvas shows the LATEST artifact** (its latest version). Older artifacts remain
  reachable via inline cards in their messages. (No multi-artifact switcher in the
  canvas for v1.1.)
- **Render: a sandboxed `<iframe>`** — `sandbox="allow-scripts allow-modals"` (NO
  `allow-same-origin`), so the report's JS runs in an **opaque origin**, walled from
  the app (no access to the auth token/cookies). A CSP limits egress.
- **Persisted:** each version's HTML stored as a blob + an artifact/version record
  linked to the session + the producing assistant message → survives reload.
- **PDF: client-side print** (`iframe.contentWindow.print()` → "Save as PDF").
  Accepted caveat: heavily-interactive JS charts may print imperfectly. No headless
  browser, no new infra.
- **`artifact` SSE event** (the rich-output extension the locked spec anticipated):
  carries metadata `{type:"artifact", artifactId, version, title}`; the HTML is
  fetched separately via an authed endpoint (HTML can be large — keep it out of the
  event stream).
